# GitHub Wiki Sync for MkDocs + mkdocstrings

This guide documents a production pattern for automatically syncing documentation from a repository into GitHub Wiki, including API content generated by `mkdocstrings`.

The key design point is: **render with MkDocs first, then sync rendered content to Wiki**. This avoids raw `::: module.symbol` blocks appearing in the Wiki.

## Quick Start

```bash
./scripts/setup-wiki-sync.sh owner/repo-name
```

## What This Automation Actually Does

On every docs-relevant push to `main`, the workflow:

1. Builds docs with `mkdocs build`.
2. Reads each source file in `docs/**/*.md`.
3. Finds the corresponding rendered HTML in `site/`.
4. Extracts main content from MkDocs HTML (`article.md-content__inner` fallback to `main`/`body`).
5. Converts that HTML back to markdown (`markdownify`).
6. Rewrites internal links to GitHub Wiki-safe page names.
7. Handles case-insensitive page-name collisions.
8. Writes Wiki pages + `_Sidebar.md` + `_Footer.md`.
9. Commits/pushes only when content changed.

Result: GitHub Wiki contains rendered API docs (including `mkdocstrings` output), not unresolved directives.

## Requirements

- `bash` 4.0+
- `gh` CLI authenticated (`gh auth login`)
- `git`
- `mkdocs.yml` + `docs/` + installable project source for mkdocstrings imports
- GitHub Wiki initialized once (manual one-time step)

## Required Workflow Dependencies

The workflow install step must include these packages:

```bash
pip install mkdocs mkdocs-material "mkdocstrings[python]" pymdown-extensions beautifulsoup4 markdownify
```

Why these matter:

- `mkdocs` + `mkdocstrings[python]`: renders API docs from docstrings.
- `beautifulsoup4`: extracts only main page content from rendered HTML.
- `markdownify`: converts rendered HTML back to markdown that Wiki accepts.

## Trigger Configuration

The workflow should run on docs and API source changes:

```yaml
on:
  push:
    branches:
      - main
    paths:
      - 'docs/**'
      - 'src/lab_drivers/**/*.py'   # adjust for your code path
      - 'mkdocs.yml'
      - 'pyproject.toml'
  workflow_dispatch:
```

Use `workflow_dispatch` for manual reruns and validation.

## One-Time Wiki Initialization

GitHub does not create `<repo>.wiki.git` until the Wiki has at least one page.

1. Open `https://github.com/owner/repo/wiki`
2. Create/save any page once
3. Re-run workflow

If missing, checkout of `${{ github.repository }}.wiki` will fail.

## Core Implementation Details

### 1) Render-first path mapping

A source doc path maps to a route and rendered HTML location:

- `docs/index.md` → `site/index.html`
- `docs/foo/index.md` → `site/foo/index.html`
- `docs/foo/bar.md` → `site/foo/bar/index.html` (fallback `site/foo/bar.html`)

This is why the workflow can preserve MkDocs routing while still generating flat Wiki pages.

### 2) Stable Wiki page naming

Page names are derived from each docs file stem, with special handling:

- `docs/index.md` → `Home.md`
- Collisions resolved case-insensitively
- If stem collisions occur, path-based names are used (e.g. `api-visa-dl3021`)
- If still colliding, suffixes are appended (`-2`, `-3`, ...)

This avoids GitHub Wiki URL ambiguity on case-insensitive paths.

### 3) Link rewriting logic

After HTML→markdown conversion, internal markdown links are rewritten so Wiki links resolve:

- Accepts `.md`, `.html`, and route-style links.
- Resolves relative and absolute links (`./`, `../`, `/...`).
- Converts to target Wiki page names (e.g. `api/visa/dl3021.md` → `dl3021` or collision-safe name).
- Leaves external URLs (`https://`, `mailto:`) and in-page anchors unchanged.

### 4) Content extraction from rendered HTML

The workflow extracts article content and removes noisy UI elements:

- `a.headerlink`
- `a[aria-label='Permanent link']`
- `.md-content__button`
- `.mdx-badge`

This keeps Wiki markdown focused on documentation content, not theme chrome.

### 5) Safety behavior

- Runs `mkdocs build` before sync.
- Fails fast if Wiki repo isn’t initialized.
- Commits only when `git status --porcelain` shows changes.
- Uses `[skip ci]` in Wiki commit message.

## How to Verify in a New Project

1. Add a page with only a mkdocstrings directive, e.g.:

   ```md
   # API Smoke Test

   ::: your_package.your_module.YourClass
   ```

2. Push to `main` (or run `workflow_dispatch`).
3. Inspect wiki page output.

Success criteria:

- Contains rendered method/class docs.
- Does **not** contain raw `:::` directive text.
- Internal links resolve to existing Wiki pages.

## Troubleshooting

### Raw `:::` appears in Wiki

Cause: syncing raw `docs/*.md` instead of rendered HTML-derived markdown.

Fix: ensure workflow uses `site/` extraction + `markdownify` conversion.

### Workflow green but missing expected API content

Check:

- `mkdocs.yml` plugin config includes `mkdocstrings`.
- Python import path is valid during CI (`handlers.python.paths`).
- Source modules are importable in runner environment.

### Wiki links 404

Check:

- link rewrite function handles `.md`/`.html`/route forms
- case-collision handling is enabled
- destination page exists after name normalization

### Checkout Wiki repo fails

Initialize Wiki once from GitHub UI, then rerun.

## Important Operational Rule

Treat `docs/` as the source of truth.

Do not manually edit GitHub Wiki pages; the next sync will overwrite them.
